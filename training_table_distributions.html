Source: rfp_training_data_complete_v3.csv, 1,899 rows, one per RFP, 285 columns. 268 are shown here; the 17 left out are matched line-for-line against ALWAYS_EXCLUDE in the real training script (not guessed): the identifier rfp_id; raw date strings inquiry_date/arrival_date (already decomposed into arrival_year, arrival_month, arrival_day_of_week, and the cyclical *_sin/*_cos columns shown here); account_name (identifier); the label and its duplicates — status, is_won, and quoted_adr (the ADR model's own prediction target, so it can't also be that model's input); four columns 100% missing for Lost rows and therefore trivially outcome-revealing (actual_pickup_rate, actual_fnb_per_person, actual_total_revenue, revenue_realization_pct); fnb_ratio, dropped per the training script's own comment because in this synthetic dataset it's a deterministic function of the outcome; and five more columns the script always drops (arrival_week, Displacement_Risk_Level, Demand_Tier, Arrival_DOW_Name, Account_Win_Rate_APIT) that duplicate or restate signal already carried by other kept columns. Extreme values are clipped at the 1st/99th percentile per numeric column so outliers don't compress the rest of the chart (the shape badge and skew value are computed on the full, unclipped column, not the clipped chart). Shape label: a column with only two distinct values is labeled "Binary flag" with the share that's 1, since skew/kurtosis describe continuous shapes and calling a two-point split "normal" or "flat" would be a category error. For everything else: |skew| < 0.5 with low excess kurtosis is "Approx. normal" / "Roughly symmetric"; |skew| ≥ 0.5 is skewed (≥1.5 "strongly"); very negative excess kurtosis with low skew reads as "Flat / uniform-like" — it's a heuristic, not a normality test, so check the curve itself too, since skew/kurtosis alone can't flag bimodality. Categorical columns show the top 6 categories by combined volume. Cards are grouped by topic, not by predictive importance. "Used in model" chips: the split count is a literal count of how many times that trained model's trees branch on the feature; the percentage is that count divided by the model's total split count (10,030 for ADR, 2,113 for Conversion, 1,513 for Pickup, 9,035 for F&B), so it's comparable within a model but not across models. Five columns here are re-encoded under a different name before the model ever sees them, so their chips point at that renamed feature: event_type → event_type_enc, event_format → event_format_enc, lead_source → lead_source_enc, group_size_tier → is_meeting_only + group_size_tier_clean_enc, and market_segment → 13 market_seg_* one-hot columns (Pickup only). A real finding from checking this: v3 already carries pre-baked event_format_encoded, market_segment_encoded, and lead_source_encoded columns from an earlier pass — none of the 4 deployed models read them. The training script re-derives its own encoding of the raw string column at train time instead, so those three stale columns have zero real influence on any model despite looking like ready-made inputs; their cards say so directly.
