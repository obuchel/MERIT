How the Two Models and the Optimizer Fit Together

The ADR and Conversion models run independently on the same RFP and never see each other's output — each is trained on its own feature set (18 features are shared inputs, the rest are model-specific). Their two predictions are combined only afterward, by binning every RFP into an ADR cluster × conversion cluster cell, which gives a segment-level baseline price and win probability. Time context (weekday, season, compression, demand tier) then adjusts that baseline, and the optimizer is the only component that actually picks a price and allocates rooms — it does so by searching for the price that maximizes expected profit for each segment, subject to the remaining room capacity in that time bucket.

How one RFP's price actually moves through the pipeline

Tracing ADR cluster 5 ("Mixed") in the October compression bucket step by step, using the numbers the optimizer script itself produces (fallback / ADR-cluster-only mode, matching cluster_time_pricing_recommendations.csv).

Where these numbers actually come from. This example runs in fallback mode — the two SHAP/UMAP files the script needs for real joint (ADR × conversion) segments aren't available in this environment, so it falls back to ADR clusters only (conversion_cluster_id = -1). That means this walkthrough isn't the same $282→$494 segment shown in the scatter plot elsewhere on this page, where ADR cluster 5 actually splits across 12 conversion clusters with different win probabilities and prices.

It's also worth separating what's model-derived from what's assumed within the walkthrough itself:
  • Mean ADR ($161.40) and base win probability (77.1%) come from the CLUSTERS list — a hardcoded snapshot of real clustering/model output. They're frozen at whatever they were when someone last updated the list, not recomputed live.
  • Elasticity (1.10) is not model-derived. It comes from a manually chosen array (ELASTICITIES) that decreases monotonically by cluster index — a placeholder shape, not a fitted price-sensitivity parameter. The script's own docstring flags this: "Replace the assumptions in TIME_BUCKETS, FEATURE_MULTIPLIERS, and ELASTICITIES with learned values when you have a conversion/win model." This is the piece to be most cautious about treating as "the model's answer" — it determines how far the optimizer is willing to push price, and nothing here estimates it from real booking response data.

Step 1 · Set the baseline (context) price

The anchor blends the segment's own ADR with what transient guests are currently paying:

0.70 × $161.40  +  0.30 × $230.00  =  $181.98

That anchor is then scaled for time/market conditions — compression date (+16%), peak arrival (+10%), strong transient ADR/RevPAR, high demand tier, and more. Those add up to a raw multiplier of 1.60, but the script caps it at 1.55:

$181.98 × 1.55  =  $282.07 — this is the context baseline price.

Step 2 · Estimate demand

The bucket's addressable pool is 1.6× its capacity (240 room nights). This segment holds 25.3% of historical RFP share, and a demand multiplier of 1.166 (boosted by peak arrival and demand tier, trimmed slightly for being a compression date):

240 × 0.253 × 1.166  =  70.9 potential room nights if priced at baseline.

Step 3 · Optimize under capacity

At the baseline price, win probability equals the segment's base rate (77.1%) by construction. As price rises, win probability decays at this segment's elasticity (1.10). But the optimizer isn't pricing this segment alone — it solves all 10 segments in this bucket jointly against the 150-room-night capacity constraint. Since total demand exceeds capacity here, a shared "scarcity value" gets layered on top of marginal cost until every segment's bookings sum to exactly 150.

For this segment, that scarcity pressure pushes the price all the way to the optimizer's 1.75× ceiling on baseline:

$282.07 × 1.75  =  $493.62 — the optimizer would go higher still, but hits its hard cap.

What the price/demand curve actually looks like here

Win probability (demand side) against expected profit (the optimizer's decision side), swept across a full price range for this exact segment — the supply-and-demand picture behind Steps 1–3.

win probability (left axis) expected profit (right axis) never observed historically
The win-probability curve is a smooth power-law decay with no floor — it never says "demand collapses to zero above $X," it just keeps gently falling. Because of that, the profit curve (win probability × volume × margin, net of the capacity scarcity value) is still climbing, not peaking, all the way to $620 in this chart. The optimizer's $493.62 recommendation isn't sitting at a point where the model predicts diminishing returns — it's sitting there only because MAX_PRICE_MULTIPLIER = 1.75 forces a stop. The shaded band marks prices above $230, the highest transient ADR (or cluster mean ADR) anywhere in the historical data used to build this model — everything to the right of it, including the recommended price, is pure extrapolation with no observed bookings to support it.

What happens if the conversion model's clusters go missing

The optimizer script reads two SHAP/UMAP files to build its joint (ADR × conversion) segments. If either file isn't found, it silently falls back to ADR clusters only — no error, no warning — and the conversion model's signal disappears from every price it recommends. Running the script without those files reproduces exactly that fallback.
Jan (low season) May (peak weekend) Oct (compression)
The mean ADR per cluster is identical either way — that part of the pipeline doesn't depend on the conversion model. The gap is entirely in win probability: fallback mode uses one static win rate per ADR cluster; the real segments use the conversion model's own predicted probability, averaged within each fine-grained (ADR × conversion) cell. Blending high- and low-conversion RFPs into a single ADR bucket hides the fact that part of that cluster is nearly unwinnable at any price and part is a near-certain win — so the weakest clusters (0-2) end up priced 24-45% too low, while the strongest clusters get pushed up to 12-30% too high. Net effect on this scenario: $15.6k less total profit (-10.2%) and 108 segments collapsed down to 10.
